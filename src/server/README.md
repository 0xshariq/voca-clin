# Server conventions

Phase 2 establishes small conventions for server code without creating a universal framework or selecting unapproved infrastructure providers.

## Environment and server boundaries

Import `getServerEnvironment` only from server code. Its module imports `server-only`, so server configuration cannot be pulled into a Client Component. `parseServerEnvironment` is a pure validator kept separate so it can be unit-tested without crossing the framework boundary. At this stage, `NODE_ENV` and `LOG_LEVEL` are the only settings; both have safe defaults. Add required secrets alongside the phase that introduces their actual provider, and never print their values in validation errors.

## Application errors and API responses

Use `ApplicationError` with a stable `applicationErrorCodes` value for expected application failures. Its `message` is an internal diagnostic and must not be returned directly. Route Handlers under `/api/v1` should pass caught errors to `mapApplicationError`, then serialize the returned body and status with `Response.json`. Unknown exceptions map to a generic 500 response; Zod failures map to a generic 400 response. The public shape is validated by the shared `apiErrorSchema`; request IDs are optional and are generated by trusted server context.

## Operations and composition

Represent a business operation as a named, typed function with its dependencies passed explicitly. Keep domain invariants inside their owning module and use that module's public entry point for cross-module access. Put multi-module orchestration in the application layer; avoid service locators and circular imports. The current module folders contain no concrete services, so a composition root is intentionally deferred until there are real dependencies to compose.

## Request context and logging

Use `withRequestContext` at a server request boundary to create an isolated UUID correlation ID. The structured `logger` includes that ID automatically and accepts only operational fields such as route templates, status codes and durations. Log static event names and route templates; never log request bodies, learner content, credentials, secrets or raw exception messages.
